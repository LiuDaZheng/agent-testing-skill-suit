# 测试设计技术详解

## 1. 等价类划分（Equivalence Partitioning）

### 定义
将输入域划分为若干等价类，从每个类中选择少量代表性数据作为测试用例。

### 原则
- 同一等价类中的数据在测试中作用等价
- 每个等价类至少设计一个测试用例
- 区分有效等价类和无效等价类

### 示例：手机号验证

**有效等价类**：
- 11 位数字
- 以 1 开头
- 第二位是 3-9

**无效等价类**：
- 少于 11 位
- 多于 11 位
- 非数字字符
- 以 0 或 2 开头
- 第二位是 0/1/2

**测试用例**：
```
TC-001: 13800138000 (有效)
TC-002: 1380013800 (10 位，无效)
TC-003: 138001380001 (12 位，无效)
TC-004: 1380013800a (含字母，无效)
TC-005: 03800138000 (以 0 开头，无效)
TC-006: 12800138000 (第二位是 2，无效)
```

## 2. 边界值分析（Boundary Value Analysis）

### 定义
对输入域的边界进行测试，因为错误往往发生在边界附近。

### 原则
- 对于范围 [min, max]，测试：min-1, min, min+1, normal, max-1, max, max+1
- 关注上边界和下边界

### 示例：密码长度 6-20 位

**边界测试点**：
```
TC-001: 5 位 (边界外，无效)
TC-002: 6 位 (边界上，有效)
TC-003: 7 位 (边界内，有效)
TC-004: 19 位 (边界内，有效)
TC-005: 20 位 (边界上，有效)
TC-006: 21 位 (边界外，无效)
```

### 示例：年龄输入 18-60 岁

**边界测试点**：
```
TC-001: 17 岁 (边界外，无效)
TC-002: 18 岁 (边界上，有效)
TC-003: 19 岁 (边界内，有效)
TC-004: 59 岁 (边界内，有效)
TC-005: 60 岁 (边界上，有效)
TC-006: 61 岁 (边界外，无效)
```

## 3. 判定表测试（Decision Table Testing）

### 定义
分析多个条件组合及其对应的动作，生成测试用例覆盖所有组合。

### 步骤
1. 列出所有条件桩（Conditions）
2. 列出所有动作桩（Actions）
3. 生成条件组合（2^n 种）
4. 简化冗余组合

### 示例：登录功能

**条件**：
- C1: 手机号格式正确
- C2: 验证码正确
- C3: 账户未锁定

**动作**：
- A1: 允许登录
- A2: 拒绝登录
- A3: 显示错误提示

**判定表**：
| 规则 | C1 | C2 | C3 | A1 | A2 | A3 |
|------|----|----|----|----|----|----|
| R1 | Y | Y | Y | ✓ | | 显示成功 |
| R2 | Y | N | Y | | ✓ | 验证码错误 |
| R3 | N | Y | Y | | ✓ | 手机号错误 |
| R4 | Y | Y | N | | ✓ | 账户锁定 |
| R5 | N | N | Y | | ✓ | 手机号错误 |
| R6 | N | Y | N | | ✓ | 手机号错误 |
| R7 | Y | N | N | | ✓ | 验证码错误 |
| R8 | N | N | N | | ✓ | 手机号错误 |

**简化后**：
- 手机号错误时，其他条件无关紧要
- 手机号正确 + 验证码错误 → 验证码错误
- 手机号正确 + 验证码正确 + 账户锁定 → 账户锁定
- 全部正确 → 登录成功

## 4. 状态转换测试（State Transition Testing）

### 定义
测试系统在不同状态之间的转换，验证状态转换是否符合预期。

### 步骤
1. 识别所有状态
2. 识别状态转换事件
3. 识别转换动作
4. 设计覆盖所有转换的测试用例

### 示例：订单状态

**状态**：
- 待支付 (Pending)
- 已支付 (Paid)
- 发货中 (Shipping)
- 已完成 (Completed)
- 已取消 (Cancelled)
- 已退款 (Refunded)

**状态转换图**：
```
待支付 → 已支付 (支付成功)
待支付 → 已取消 (用户取消/超时)
已支付 → 发货中 (商家发货)
已支付 → 已退款 (用户申请退款)
发货中 → 已完成 (用户确认收货)
发货中 → 已退款 (退货退款)
```

**测试路径**：
```
TC-001: 正常路径
  待支付 → 已支付 → 发货中 → 已完成

TC-002: 取消路径
  待支付 → 已取消

TC-003: 退款路径 1
  已支付 → 已退款

TC-004: 退款路径 2
  已支付 → 发货中 → 已退款
```

## 5. 场景测试（Use Case Testing）

### 定义
基于用户旅程和业务场景设计测试用例，覆盖主流程、备选流程和异常流程。

### 步骤
1. 识别主要参与者
2. 识别主要场景
3. 识别备选场景
4. 识别异常场景
5. 设计测试用例

### 示例：购物流程

**参与者**：顾客

**主流程**：
```
1. 浏览商品
2. 查看商品详情
3. 加入购物车
4. 结算
5. 选择支付方式
6. 完成支付
7. 确认订单
```

**备选流程**：
```
A1: 使用优惠券
  4a. 选择优惠券
  4b. 应用优惠
  4c. 继续结算

A2: 修改收货地址
  4a. 选择新地址
  4b. 确认地址
  4c. 继续结算

A3: 选择不同支付方式
  5a. 选择微信支付
  5b. 完成微信支付
  
  或
  
  5a. 选择支付宝
  5b. 完成支付宝支付
```

**异常流程**：
```
E1: 库存不足
  3a. 检查库存
  3b. 库存不足，提示用户
  
E2: 支付失败
  6a. 支付处理
  6b. 支付失败，提示用户
  6c. 返回支付页面
  
E3: 网络超时
  任意步骤：网络超时
  提示用户重试
```

**测试用例**：
```
TC-001: 正常购物流程 (主流程)
TC-002: 使用优惠券购物 (备选 A1)
TC-003: 修改地址购物 (备选 A2)
TC-004: 微信支付 (备选 A3)
TC-005: 库存不足处理 (异常 E1)
TC-006: 支付失败处理 (异常 E2)
TC-007: 网络超时处理 (异常 E3)
```

## 技术选择决策树

```
AC 特征分析
    ↓
有明确的输入范围？
    ├─ 是 → 边界值分析
    └─ 否 → 继续分析
         ↓
有多个输入类别？
    ├─ 是 → 等价类划分
    └─ 否 → 继续分析
         ↓
有多个条件组合？
    ├─ 是 → 判定表测试
    └─ 否 → 继续分析
         ↓
有状态变化？
    ├─ 是 → 状态转换测试
    └─ 否 → 继续分析
         ↓
是端到端流程？
    ├─ 是 → 场景测试
    └─ 否 → 使用等价类 + 边界值
```

## 组合使用示例

### 示例：用户注册功能

**AC**：
- 用户名：3-20 个字符，只能包含字母数字下划线
- 密码：6-20 位，必须包含字母和数字
- 邮箱：有效邮箱格式
- 手机号：11 位数字

**测试设计**：

1. **用户名**：边界值 + 等价类
   - 边界：2 位、3 位、4 位、19 位、20 位、21 位
   - 等价类：有效字符、特殊字符、中文

2. **密码**：边界值 + 判定表
   - 边界：5 位、6 位、7 位、19 位、20 位、21 位
   - 组合：只有字母、只有数字、字母 + 数字

3. **邮箱**：等价类
   - 有效格式、无效格式、空值

4. **手机号**：边界值 + 等价类
   - 边界：10 位、11 位、12 位
   - 等价类：有效号段、无效号段、非数字

**测试用例总数**：约 20-30 个
