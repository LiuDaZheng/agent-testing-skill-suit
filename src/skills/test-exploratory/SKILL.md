# 探索式测试 Skill (test-exploratory)

## 核心概念

**探索式测试**是一种经验型测试方法，测试人员同时设计、执行和记录测试，依靠测试人员的技能、创造力和对系统的理解来发现缺陷。

### 关键术语
- **测试章程 (Test Charter)**: 探索式测试的任务说明书
- **会话 (Session)**: 有时间限制的探索式测试时间段
- **会话管理 (Session-Based Test Management, SBTM)**: 结构化的探索式测试方法
- **测试启发法 (Test Heuristics)**: 测试中的经验法则和思维模型
- **测试游览 (Test Tours)**: 有主题的探索路径

## 使用场景

✅ 适用场景:
- 敏捷开发快速迭代
- 新功能的早期测试
- 回归测试的补充
- 发现意外缺陷
- 测试时间有限
- 需求不明确或频繁变更

❌ 不适用:
- 需要严格文档的合规测试
- 重复性高的回归测试 (应自动化)
- 安全关键系统的形式化验证

## 探索式测试 vs 脚本测试

| 维度 | 脚本测试 | 探索式测试 |
|------|---------|-----------|
| 设计时间 | 执行前 | 执行中 |
| 执行方式 | 按步骤 | 自由探索 |
| 文档程度 | 详细 | 轻量 |
| 覆盖率 | 可测量 | 基于章程 |
| 发现缺陷 | 预期内 | 意外发现 |
| 适用阶段 | 回归/验收 | 早期/敏捷 |

## 测试章程设计

### 章程结构模板

```
探索 <区域/功能/风险>
使用 <资源/启发法/工具>
以发现 <信息类型>
```

### 章程示例

```markdown
好的章程:
✅ "探索登录功能，使用不同浏览器和设备，以发现兼容性问题"
✅ "探索购物车结算流程，使用大额订单和优惠券组合，以发现计算错误"
✅ "探索搜索功能，使用特殊字符和超长输入，以发现边界问题"

不好的章程:
❌ "测试登录功能" (太宽泛)
❌ "用用户名 admin 和密码 123 登录，点击确定，验证跳转" (太具体，变成脚本)
```

## 测试启发法

### 常用启发法模型

#### 1. CRUD 启发法
- **C**reate: 创建新数据
- **R**ead: 查看/查询数据
- **U**pdate: 修改数据
- **D**elete: 删除数据

#### 2. 边界值启发法
- **零**: 空值、零数量
- **一**: 单个项目
- **多**: 大量数据
- **最大**: 系统上限

#### 3. 时间相关启发法
- **并发**: 同时操作
- **顺序**: 操作顺序变化
- **超时**: 长时间等待
- **速率**: 快速连续操作

#### 4. 用户角色启发法
- **新手用户**: 不熟悉系统
- **专家用户**: 高效使用
- **恶意用户**: 尝试破坏
- **特殊需求**: 无障碍使用

### James Bach 的 SFDPOT 模型

```
S - Structure (结构): 产品由什么组成
F - Function (功能): 产品能做什么
D - Data (数据): 产品处理什么数据
P - Platform (平台): 产品依赖什么环境
O - Operations (操作): 产品如何被使用
T - Time (时间): 产品如何随时间变化
```

## 测试游览 (Test Tours)

### 常见游览类型

| 游览名称 | 目标 | 示例章程 |
|---------|------|---------|
| 地标游览 | 覆盖主要功能 | "探索所有主菜单功能" |
| 导游游览 | 跟随用户指南 | "按照用户手册完成所有示例" |
| 糟糕邻居游览 | 测试问题高发区 | "探索历史 bug 最多的模块" |
| 反社会游览 | 破坏性测试 | "尝试让系统崩溃" |
| 博物馆游览 | 测试老旧代码 | "探索很久没改动的功能" |
| 超级模特游览 | 关注 UI/UX | "探索所有页面的视觉效果" |
| 强迫症游览 | 重复操作 | "反复点击同一按钮 100 次" |
| 背包客游览 | 深入某个功能 | "深度探索搜索算法" |

### 示例 3: API 探索测试

```python
# API 探索测试章程

"""
章程：探索用户管理 API
使用：curl/Postman + 自动化脚本
发现：认证、授权、输入验证问题
"""

# 测试思路
test_ideas = [
    # 认证测试
    "无 token 访问受保护接口",
    "过期 token 访问",
    "无效 token 格式",
    "不同用户 token 混用",

    # 输入验证
    "超长字符串输入",
    "特殊字符注入",
    "SQL 注入尝试",
    "XSS  Payload",
    "负数 ID",
    "超大页码",

    # 边界测试
    "创建 0 个资源",
    "创建最大允许数量",
    "批量操作边界",

    # 并发测试
    "同时创建相同资源",
    "同时修改同一资源",
    "同时删除有依赖资源",
]

# 执行记录
class ExploratorySession:
    def __init__(self):
        self.findings = []
        self.start_time = datetime.now()

    def log_finding(self, idea, result, severity):
        self.findings.append({
            'idea': idea,
            'result': result,
            'severity': severity,
            'timestamp': datetime.now()
        })

    def report(self):
        print(f"探索测试报告 - {len(self.findings)} 个发现")
        for f in self.findings:
            print(f"[{f['severity']}] {f['idea']}: {f['result']}")
```

## 会话管理最佳实践

### 1. 时间盒管理
- 推荐时长：60-120 分钟
- 包含：准备 (10%) + 执行 (70%) + 总结 (20%)
- 避免疲劳，适当休息

### 2. 记录策略
- 测试中：简要笔记 + 截图
- 测试后：整理详细报告
- 使用工具：截图工具、录屏、笔记应用

### 3. 章程评审
- 测试前：与团队确认章程
- 测试后：分享发现和洞见
- 持续改进：基于反馈优化章程

### 4. 覆盖率跟踪
- 记录已探索区域
- 识别未覆盖区域
- 规划后续会话

## 验收标准检查清单

- [ ] 测试章程清晰明确
- [ ] 章程数量适当 (3-5 个/会话)
- [ ] 应用了测试启发法
- [ ] 有时间盒限制
- [ ] 有会话记录
- [ ] 有发现总结报告
- [ ] Bug 已提交跟踪
- [ ] 文档包含至少 5 个使用示例
- [ ] 引用来源清晰标注

## 常见陷阱

⚠️ **无目标漫游**: 没有章程，盲目测试 → 制定明确章程
⚠️ **过度文档**: 记录太详细影响探索 → 轻量记录
⚠️ **时间失控**: 超出时间盒 → 严格计时
⚠️ **发现不跟踪**: bug 未提交 → 及时记录跟踪
⚠️ **重复测试**: 多次相同探索 → 记录覆盖区域

## 工具推荐

- **会话管理**: Session Tester, SBTM 工具
- **记录工具**: Snagit, Loom, Notion
- **Bug 跟踪**: Jira, GitHub Issues
- **协作**: Miro (思维导图), Confluence
