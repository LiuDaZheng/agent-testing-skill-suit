# 需求缺陷检查清单

## 常见需求缺陷类型

### 1. 模糊不清（Ambiguity）
**特征**：使用主观、无法量化的词汇
- ❌ "系统应该快速响应"
- ✅ "系统应在 2 秒内响应"

**检查问题**：
- 是否包含"快速"、"友好"、"高效"等主观词？
- 是否有明确的量化指标？

### 2. 不可测试（Un-testable）
**特征**：没有明确的验收标准
- ❌ "用户体验要好"
- ✅ "用户完成注册流程不超过 3 步"

**检查问题**：
- 能否设计测试用例验证此需求？
- 是否有明确的通过/失败标准？

### 3. 矛盾冲突（Contradiction）
**特征**：不同需求之间相互矛盾
- 需求 A："数据实时同步"
- 需求 B："支持离线模式"

**检查问题**：
- 与其他需求是否冲突？
- 与系统架构是否一致？

### 4. 缺失遗漏（Missing）
**特征**：关键场景未覆盖
- 只描述了正常流程，缺少异常处理
- 只描述了功能，缺少性能要求

**检查问题**：
- 异常场景是否覆盖（网络失败、数据无效等）？
- 边界条件是否定义？
- 安全需求是否考虑？

### 5. 过度详细（Over-specified）
**特征**：限制了实现方案而非结果
- ❌ "使用 MySQL 数据库，表结构如下..."
- ✅ "数据持久化，支持事务，查询响应<100ms"

**检查问题**：
- 是否限制了技术实现方案？
- 是否应该只定义"做什么"而非"怎么做"？

## 需求评审检查表

```markdown
## 完整性检查
- [ ] 所有功能模块都有需求描述
- [ ] 异常场景已覆盖
- [ ] 边界条件已定义
- [ ] 安全需求已考虑

## 清晰性检查
- [ ] 无模糊词汇（快速、友好、高效）
- [ ] 所有指标可量化
- [ ] 术语定义一致

## 可测试性检查
- [ ] 每个需求都有验收标准
- [ ] 可设计测试用例验证
- [ ] 测试数据可获得

## 一致性检查
- [ ] 需求之间无矛盾
- [ ] 与系统架构一致
- [ ] 与业务目标一致

## 优先级检查
- [ ] 所有需求都有优先级标注
- [ ] 优先级与业务价值匹配
- [ ] 高优先级需求已识别
```

## 需求缺陷报告模板

```markdown
### 缺陷 ID: DEF-REQ-001
- **需求 ID**: REQ-003
- **缺陷类型**: 模糊不清
- **问题描述**: "系统响应要快"没有量化标准
- **影响**: 无法设计性能测试用例
- **建议修改**: "系统在 95% 的情况下应在 2 秒内响应"
- **严重程度**: Medium
- **状态**: Open
```
